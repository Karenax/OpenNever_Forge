0. Tutoriel de bout en bout

Ce parcours part d’un MOD existant, ajoute une zone et un script, prouve la construction puis prépare un test en jeu. Il indique à chaque étape le contrôle exact à utiliser et ce que vous devez observer avant de continuer.

Préparez une copie. Ne sélectionnez jamais comme source votre seul exemplaire du module. OpenNever protège la source, mais le tutoriel produit volontairement de nouveaux fichiers et un déploiement de test.

Les trois chemins à ne pas confondre

ChampExempleRôle précis
Module NWNE:\MesModules\copie_test.modConteneur ERF lu comme source immuable. Il fournit l’état de référence.
Installation du jeu…\steamapps\common\Neverwinter NightsRacine du moteur, des ressources officielles et de nwn_script_comp.
Données utilisateur…\Documents\Neverwinter NightsRacine des dossiers development, hak, modules, override et tlk.

A. Analyser et créer l’atelier

  1. Dans Table de campagne, renseignez les trois chemins avec les boutons Parcourir. Ils sont enregistrés localement et restaurés au prochain démarrage.
  2. Cliquez sur Analyser la copie. Attendez 100 % : fermer l’application pendant l’indexation laisse l’opération incomplète.
  3. Contrôlez les compteurs de ressources, les HAK/TLK déclarés et les messages de Diagnostics. Une dépendance manquante doit être comprise avant l’édition.
  4. Cliquez sur Créer l’espace d’édition. À partir de cet instant, les écritures ciblent l’overlay transactionnel, pas le MOD source.

Résultat attendu : Module analysé et Atelier créé indiquent Prêt ; le catalogue est rempli et les ateliers d’édition sont accessibles.

B. Créer une zone minimale

  1. Ouvrez Zones, puis + Nouvelle zone.
  2. Choisissez un ResRef en minuscules, sans espace et limité à 16 caractères, par exemple tuto_zone. Saisissez un nom visible, un tileset résolu et des dimensions modestes pour le premier essai.
  3. Cliquez sur Créer ARE/GIT/GIC. Ces trois fichiers partagent le même ResRef : ARE décrit la zone, GIT ses instances et GIC ses données complémentaires.
  4. Développez + Placer une instance, choisissez une catégorie et saisissez le ResRef exact d’un blueprint existant. Renseignez X/Y pour la position horizontale, Z pour l’altitude et bearing pour l’orientation, puis cliquez sur Ajouter à la zone.
  5. Contrôlez la grille, la liste d’instances et les diagnostics du walkmesh. Un objet visible mais inaccessible indique souvent une position ou une surface marchable incohérente.

Résultat attendu : tuto_zone.are, tuto_zone.git et tuto_zone.gic apparaissent dans le workspace, avec l’instance dans la zone.

C. Modifier et compiler un script

  1. Ouvrez Scripts, sélectionnez une source et l’onglet Source NSS. Le NSS est le texte ; le NCS est le bytecode réellement exécuté.
  2. Modifiez le code, puis cliquez sur Enregistrer NSS. Tant que le texte n’est pas enregistré, la compilation reste désactivée pour éviter de compiler une version différente de l’éditeur.
  3. Corrigez les includes ou signatures signalés. Les includes sont résolus à travers le Resource Manager et ses couches.
  4. Cliquez sur Compiler NSS → NCS et lisez la sortie du compilateur. Une sauvegarde NSS réussie ne signifie pas qu’un NCS valide existe.
  5. Ouvrez Références et vérifiez que le ResRef du script est relié à l’évènement, au dialogue ou au blueprint voulu.

Résultat attendu : le NSS et le NCS sont présents dans le workspace, le NCS n’est ni Absent ni Obsolète et aucune erreur de compilation ne subsiste.

D. Valider, construire et tester

  1. Ouvrez Construction et corrigez les diagnostics bloquants. Examinez aussi chaque avertissement ; l’ignorer doit être une décision consciente.
  2. Cliquez sur Vérifier ×2. OpenNever construit deux fois le même état et compare les empreintes pour détecter une sortie non déterministe.
  3. Cliquez sur Construire et choisissez une destination distincte du MOD source. Conservez le journal de construction si une erreur apparaît.
  4. Pour tester rapidement des ressources isolées, cliquez sur Déployer development. Les fichiers copiés dans le dossier utilisateur development prennent priorité sur ceux du MOD chargé.
  5. Lancez le jeu ou le serveur avec le bon module. Une fois le test terminé, utilisez Nettoyer development : OpenNever retire seulement les fichiers enregistrés dans son manifeste.

Résultat attendu : Vérifier ×2 donne deux empreintes identiques, un nouveau MOD est produit et le déploiement live est intégralement réversible.

E. Utiliser Agent Studio sans perdre le contrôle

  1. Dans les réglages avancés, choisissez un protocole clairement indiqué comme OpenAI compatible ou Ollama, puis renseignez endpoint et modèle. La clé temporaire n’est pas enregistrée.
  2. Autorisez le réseau dans la politique, puis cliquez sur Tester la communication avec le modèle. Corrigez l’endpoint, la clé ou le nom du modèle tant que ce test ne réussit pas.
  3. Décrivez un objectif vérifiable et cliquez sur Préparer l’exécution. Cette action crée une carte persistée mais ne contacte pas encore le modèle.
  4. Dans cette carte, cliquez sur Lancer l’agent. L’indicateur animé et la bannière décrivent le travail actif ; le journal précise les tours, appels et éventuelles attentes.
  5. Relisez les opérations et approuvez seulement celles attendues. Une capacité interdite, un budget dépassé ou une approbation manquante doit arrêter ou suspendre le flux.

Résultat attendu : le test fournisseur réussit, l’exécution quitte l’état planned après Lancer l’agent et toute modification passe par les transactions locales.

Partie I · Utilisateur

1. Présentation

OpenNever Forge est un atelier local pour Neverwinter Nights: Enhanced Edition. Il réunit analyse, édition structurée, construction, test live et assistance IA contrôlée sans modifier le module d’origine.

Comprendre

Catalogue, provenance, références, dialogues, scripts, carte 2D, scène 3D et rapport global.

Modifier

GFF, blueprints, DLG, journal, factions, zones, instances, walkmeshes, 2DA, TLK et NSS.

Livrer

Validation, NSS→NCS, MOD/HAK/TLK déterministes, profils et dossier development.

Automatiser

IA à permissions fines, budgets, approbations, audit, checkpoint et reprise.

Invariant absolu : le fichier NWN sélectionné comme source n’est jamais écrit. Les changements vivent dans une copie, un overlay ou un nouvel artefact.

Les fondations lecture seule, l’édition transactionnelle, les pipelines de build, la synchronisation Toolset, les migrations et l’orchestrateur IA sont implémentés. Les limites de recette encore connues sont détaillées au chapitre 24.

5. Premier parcours

  1. Choisir le .mod, la racine d’installation et le dossier utilisateur.
  2. Lancer l’analyse : empreinte, index ERF et résolution des ressources.
  3. Créer l’espace d’édition transactionnel.
  4. Inspecter provenance et dépendances avant toute modification.
  5. Modifier avec les éditeurs structurés puis compiler chaque NSS changé.
  6. Valider le module et construire deux fois pour vérifier la reproductibilité.
  7. Tester via development ou un profil client/serveur.

Overlay versionné

7. Éditer un module

Une commande lit l’état, valide l’entrée, crée une révision adressée par contenu, ajoute une entrée au journal et met à jour l’overlay. Annuler/Rétablir déplace la tête logique sans écrire la source.

  • champs GFF avec préservation des inconnus ;
  • blueprints, dialogues, journal et factions ;
  • TLK et 2DA avec validation de structure ;
  • ajout, remplacement ou suppression logique ;
  • dépendances HAK/TLK ;
  • création d’un module, de zones et d’instances via palettes.
Conseil : créez un checkpoint avant une synchronisation Toolset, une transformation de walkmesh ou une exécution autonome.
NSS → NCS

8. Scripts NWScript

Le NSS est édité dans l’overlay. Le NCS est une sortie dérivée obligatoire. La fraîcheur dépend du hash du NSS, de tous ses includes et du compilateur configuré.

  1. Ouvrir ou créer le NSS.
  2. Corriger les diagnostics et contrôler les includes résolus.
  3. Choisir le compilateur et ses arguments autorisés.
  4. Compiler par lancement direct, sans shell.
  5. Vérifier l’empreinte du NCS produit.
Blocage volontaire : build, sync Toolset et déploiement sont refusés si un NSS modifié ne possède pas un NCS frais.
Zones et navigation

9. Monde, zones et walkmeshes

Une zone coordonne ARE (propriétés), GIT (instances) et GIC (compléments). La carte 2D modifie position, orientation et identité de ressource en conservant leurs formats distincts.

Les lecteurs WOK/PWK/DWK exposent sommets, faces, adjacences et matériaux. Les transformations et writers valident indices, topologie et bornes. Une édition structurelle doit toujours être contrôlée dans le Toolset et le jeu.

Sorties

10. Construire, déployer et tester

Le builder fusionne source, dépendances résolues et overlay dans un nouvel artefact. L’ordre des entrées et les métadonnées sont stabilisés ; l’écriture finale est atomique.

  • Vérifier ×2 : deux builds, deux hashes comparés ;
  • Profils : chemins, cible, client ou serveur ;
  • Git : suivi du workspace sans modules propriétaires ;
  • Development : surcharge live sans reconstruire le MOD.
Nettoyage sûr : seuls les fichiers déployés dont le hash est encore attendu sont supprimés. Une modification manuelle est préservée.

Les profils lancent client ou serveur avec une liste d’arguments directe, jamais via un interpréteur de commandes.

Interopérabilité

11. Aurora Toolset

  1. Ouvrir le module dans les deux applications.
  2. Comparer confronte Toolset, OpenNever et baseline.
  3. Résoudre manuellement les conflits ambigus.
  4. Synchroniser après création d’une sauvegarde .opennever-backups.

Assistance contrôlée

12. IA et Agent Studio

La salle IA propose deux usages distincts. À gauche, Agent multi-étapes construit ou transforme plusieurs éléments en appelant les outils autorisés. À droite, Assistant contrôlé demande une seule proposition ciblée sur des champs GFF ou un script NSS ; il ne construit pas un module complet.

Lancer l’agent multi-étapes

  1. Ouvrez les réglages avancés, choisissez le fournisseur et le nom exact du modèle, puis autorisez le réseau.
  2. Décrivez le résultat attendu et cliquez sur Préparer l’exécution. Cette étape enregistre le plan et ses limites, sans contacter le modèle.
  3. Dans l’exécution préparée, cliquez sur Lancer l’agent. L’indicateur animé confirme que le modèle travaille ; un modèle local volumineux peut demander plusieurs minutes.
  4. Répondez aux demandes d’approbation et consultez le journal. Les erreurs sont aussi affichées directement dans le panneau.

Utiliser l’assistant contrôlé

  1. Renseignez endpoint, modèle et demande.
  2. Autorisez l’appel réseau et seulement les données nécessaires.
  3. Cliquez sur Générer et prévisualiser, relisez chaque opération, puis confirmez son application.

Résolution rapide

13. Dépannage

Des ressources semblent absentes

Vérifiez racines, langue, HAK/TLK et provenance ; une surcharge development/override peut masquer la ressource.

Build bloqué par un script

Recompilez après modification du NSS ou d’un include et vérifiez le compilateur configuré.

Changements Toolset perdus

Après sync, faites F7 puis sauvegardez le module avant fermeture.

Modification live invisible

Contrôlez dossier development, resref, type et ressources plus prioritaires.

Outil IA refusé

Contrôlez capacité, approbation, scope, budget et permission d’action externe.

Migration échouée

Ne modifiez pas SQLite à la main ; restaurez la sauvegarde byte-for-byte et lisez l’historique.

Résolution

17. Resource Manager

La clé est (resref normalisé, type u16). Le gagnant et toutes les variantes masquées conservent chemin, conteneur, taille et hash.

Priorité forte → faible

  1. development utilisateur ;
  2. override utilisateur ;
  3. lang/<lang>/data/ovr puis ovr de l’installation ;
  4. MOD actif ;
  5. HAK déclarés, premier le plus fort ;
  6. KEY de patch explicites ;
  7. KEY/BIF retail et base, localisés puis généraux, ordre stable.

Conserver les candidats masqués explique les différences entre machines et les surcharges inattendues.

Persistance

18. Édition transactionnelle

Le contenu est adressé par hash. Les révisions pointent vers ces objets ; le journal append-only enregistre intention, application et résultat. Les suppressions sont des tombstones. Une intention interrompue est détectée à la reprise et une action externe n’est jamais rejouée aveuglément.

Les écritures finales utilisent un temporaire sur le même volume, validation puis remplacement. Schémas : v1 initial, v2 révisions/suppressions/récupération, v3 historique et baselines Toolset. Une sauvegarde byte-for-byte précède la migration ; une version future est refusée.

ModuleBlueprint

Le plan est un DAG déclaratif de ressources et dépendances, validé avant application. Chaque nœud produit un résultat auditable.

{
  "module": {"name":"La Crypte oubliée","tag":"crypt_demo"},
  "resources": [
    {"id":"area_crypt","kind":"area","resref":"crypt01"},
    {"id":"npc_guard","kind":"creature","resref":"crypt_guard"},
    {"id":"dlg_guard","kind":"dialogue","resref":"crypt_guard"}
  ],
  "dependencies": [
    {"from":"npc_guard","to":"dlg_guard","relation":"conversation"}
  ]
}

Les runs vivent sous <workspace>/agent. Une étape interrompue n’est ni réussie ni automatiquement rejouée ; le checkpoint cohérent sert de reprise.

Interopérabilité locale

21. Serveur MCP

opennever-mcp fonctionne en stdio local, sans port réseau. Il prend en charge MCP 2025-11-25 et 2025-06-18. Le client lance le processus, négocie initialize, envoie la notification, liste puis appelle outils/ressources. Tous les appels traversent politique et budgets.

{
  "mcpServers": {
    "opennever-forge": {
      "command": "E:/OpenNever_Forge/target/release/opennever-mcp.exe",
      "args": ["--workspace", "E:/MesModules/Crypte.opennever"]
    }
  }
}

Messages limités à 4 Mio, URI contrôlées et sous-ensemble sûr. MCP ne contourne aucune approbation. Utilisez MCP pour un agent externe ; utilisez les providers intégrés pour l’expérience embarquée. Les deux aboutissent aux mêmes services Rust.

Le modèle de menace couvre archives malformées, allocations excessives, path traversal, sortie hors workspace, NCS périmé, replay interrompu, effacement live non sûr et escalade IA implicite.

Le projet est Apache-2.0. Les modules utilisateur, l’installation NWN et les contenus propriétaires ne sont pas distribués. Les dépendances liées doivent être compatibles ; certains outils restent des processus externes.
